# 17 — Analytics Event Taxonomy (PHI-free)

> **Repo se jo mila (✅):** PostHog client (`featureFlags.ts` me `identify/capture`; autocapture off, memory persistence, replay off — pichhle push me), Unleash flags, Prometheus metrics (`prom-client`), Sentry (scrubbed). Backend `AuditLog` (security/audit, analytics nahi).
> **Rule #1:** analytics me **koi PHI/PII nahi** — na naam, phone, email, diagnosis, medicine, report content, exact address/location, free-text queries jo health condition ho sakti hain.
> **Goal:** ek consistent event dictionary taaki funnels, cohorts, experiments aur provider dashboards sab same definitions use karein.

---

## 1. Principles

1. **Event allowlist** — sirf documented events/properties jaate hain; unknown properties server-side/SDK-side drop (schema validation).
2. **Pseudonymous IDs** — `distinct_id = HMAC(userId, secret)`; secret rotate-able; raw userId/phone/email kabhi nahi.
3. **Coarse values only** — city (not address), age band (not DOB), price band (not exact when sensitive), `category_code` (not search text).
4. **Sensitive categories (mental health, sexual health, de-addiction, fertility, HIV/STD, women's health):** events **count-only** (no category-level detail in third-party analytics); keep deeper analysis first-party, aggregated, k-anonymised.
5. **Consent-aware** — analytics beyond essential respects user consent; "Do Not Track"/opt-out honoured; children's accounts: no behavioural analytics.
6. **Server-side events for money/state changes** (source of truth); client events for UI/behaviour.
7. **Version everything** (`schema_version`), naming convention stable, deprecate don't rename.
8. **Retention limits** (e.g., raw events 13 months, aggregates longer), region/vendor documented in DPIA.

## 2. Naming convention

`<object>_<action>` in `snake_case`, past tense for completed actions.
Examples: `search_performed`, `provider_viewed`, `booking_created`, `payment_succeeded`, `join_step_completed`.
Property names `snake_case`, typed (string/number/bool/enum), units explicit (`amount_inr`, `duration_min`).

## 6. Experimentation (Unleash ✅ + PostHog)
- Flag → variant assignment logged as `experiment_exposed` (`flag`, `variant`).
- Guardrail metrics: booking success, refund rate, complaint rate, latency, crash-free %, no negative effect on safety/emergency flows.
- **Never experiment on:** emergency flows, consent screens (dark patterns), pricing disclosure clarity, safety messaging.
- Sample-size & duration rules; avoid peeking; ethical review for health-related UX tests.

## 7. Implementation architecture

```
Client SDK (wrapper `track(eventName, props)`)
   → schema validator (zod; allowlist per event; strips unknown/PII-like props)
   → consent gate → PostHog (cloud/self-host) + first-party sink
Server events (booking/payment/join state changes)
   → same validator → outbox → Kafka ✅ → warehouse (Trino/Pinot ✅) with pseudonymised IDs
```
- **Wrapper only** — direct `posthog.capture` calls banned (lint rule).
- **PII-detector** in validator: reject strings matching phone/email/Aadhaar/PAN patterns; max string length; enum-only for most props.
- **IDs:** `provider_id_hash` (salted hash) in third-party tools; internal warehouse can use stable internal IDs under access control.
- **Sampling:** impressions sampled/batched; session replay **off** (or masked-all for non-sensitive pages only).
- **Server-side tagging** option to keep third-party off the client (reduces leakage, ad-blockers).
- **Warehouse:** event partitioning by date; role-based access; masked views for analysts; k-anonymity thresholds (min group ≥ 10) on dashboards; no individual-level export.

## 8. Data governance
| Item | Rule |
|---|---|
| Owner | Product analytics lead + DPO sign-off for new events |
| Event registry | Single `events.yaml` (name, owner, properties, types, PII-class, retention); CI fails if code emits unregistered event |
| Review process | New event/property PR → privacy review (checklist below) |
| Retention | Raw 13 months (third-party), aggregates longer; deletion on DSR (pseudonymous ID mapping purge) |
| Access | Least privilege; audit analytics queries on raw events |
| Vendor | PostHog region/DPA documented (DPIA ✅ to-do); consider self-host for control |
| Children | Analytics off/minimal for minors |
| Third-party SDKs | None on health pages without review |

**Privacy review checklist (per event):** Can any property identify a person? Could it reveal health condition? Is it needed? Coarser alternative? Consent basis? Retention? Sensitive category → count-only?

## 9. Provider-facing analytics (separate from internal product analytics)
Provider dashboard metrics computed server-side from bookings (not from third-party analytics): views, bookings, conversion, no-show %, revenue, rating trend, response time, peak hours, repeat rate, service mix. **Aggregated; patient-level details only within care relationship.**

## 10. Alerting on analytics health
Event volume drops (instrumentation broke), schema violations spike, PII-detector hits, funnel step anomalies (payment success drop), notification failures spike, unmet-demand surges (e.g., dengue testing searches).
